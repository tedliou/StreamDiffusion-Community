# TensorRT Engines are built on the user's machine, with a PyTorch fallback

The fast path runs the UNet, tiny VAE and Upscaler as TensorRT FP16 Engines with dynamic-shape profiles covering Generation Resolutions from 256 to 1024 per side. Engines are never committed or downloaded. They are built on first use and cached under a key made of model revision, component, resolution profile, precision, export version, GPU name, compute capability and TensorRT version. While an Engine builds, the PyTorch Backend (SDPA attention) keeps producing Output Frames, so a fresh clone shows output within seconds.

An INT8 UNet (ModelOpt post-training quantisation, exported as Q/DQ) exists only as a bench option. Its profile covers just the bench matrix's 4:3 Generation Resolutions, and it does not build on an 8 GB RTX 3070 yet.

The FP16 UNet Engine also carries Temporal Coherence (#16): a `switch` input and each coherent layer's previous keys and values in, this call's out, with token counts dynamic over the same profile. One Engine serves the setting on and off, since `switch` 0 masks the previous features out, so toggling never triggers a build. The INT8 UNet stays without it. The export version is per Engine, so this change rebuilt only the FP16 UNet.

The Upscaler (#21) is a fourth Engine component, FP16 with a dynamic profile over the same Generation Resolutions. Its cache key carries the Upscaler weights' SHA-256 instead of the sd-turbo revisions and has its own export version, so adding or changing it never rebuilds the UNet or VAE Engines. It builds in about 15 s. The Engine itself takes 10 ms per frame at 512x512 on an RTX 3070 at 162 W, below the static-shape spike's 16 ms. The spike ran on the default stream and the Engine runs on the Runtime's own.

Keeping the PyTorch Backend generating during a build needs about 8 GB: its UNet and text encoder stay loaded while TensorRT holds its own copy of the weights and its workspace. In Low-VRAM Mode (#25) the build is exclusive instead: output pauses, and after each ONNX export the PyTorch UNet is released and the text encoder waits in host memory until that Engine is built. The Engines then load with the UNet still released, and output resumes on them. A failed build resumes output on the PyTorch Backend, as in the normal build. Low-VRAM Mode also caps the Model Spec at 512 px per side (#26): its Engines' profile covers 256-512, and a larger requested Generation Resolution is scaled down to fit, keeping the aspect ratio as closely as multiples of 64 allow, on both Backends. The Settings keep the requested size, so Presets stay portable, and the Runtime status reports the size in effect. The profile's sides are part of the cache key, so capped and full Engines sit side by side and an 8 GB machine rebuilds nothing. In both modes the workspace is the VRAM free just before each build, minus the ONNX weights and a 512 MiB reserve, capped at 2 GiB for FP16; with less than 256 MiB left the build fails with that reason instead of being attempted.

An Engine only runs on the GPU and TensorRT version it was built for, so shipping Engines would break on most machines; building locally costs a few minutes once.

## Considered Options

- TensorRT-RTX (JIT-compiled, portable across RTX GPUs): kept as an experiment, it is younger and its operator coverage less proven.
- torch.compile as the main path: rejected, on Windows it needs MSVC and triton-windows, which breaks the one-click setup.
- Polygraphy and ONNX Runtime as in upstream: dropped, TensorRT's own Python API covers building and running.
- TensorRT 11 (11.4): rejected for now. With a dynamic-shape profile its sd-turbo UNet Engine outputs NaN at 64x64 latents (512 px) and above. A fixed-shape profile from the same ONNX is correct, and so is TensorRT 10.16 from the same ONNX with the same dynamic profile, so the cause is TensorRT 11. Exporter choice (legacy or dynamo with the ONNX Attention op), FP32 normalisation and attention fusion (fused in both cases) were ruled out. BF16 avoids the NaN but is slower and less accurate. The Runtime pins TensorRT 10.16; retry TensorRT 11 when a release fixes it, since the Engine cache key includes the TensorRT version.
